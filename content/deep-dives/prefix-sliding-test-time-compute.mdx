## 💡 Trực Giác Bài Toán: "Hội Chứng Phình To KV-Cache" Là Gì?

Khi các mô hình AI chuyển từ việc *trả lời ngay* sang việc *suy nghĩ từng bước trước khi trả lời* (Test-Time Compute / Chain-of-Thought Reasoning như o1, GPT-6, DeepSeek R1/V4), chúng thường sinh ra hàng ngàn token suy nghĩ ẩn (`<thought> ... </thought>`).

Hãy tưởng tượng một học sinh làm toán:
* Đề bài: "Giải phương trình $x^2 + 5x + 6 = 0$".
* Học sinh viết nháp ra 10 trang giấy tính toán nhầm, gạch xóa, thử sai.
* Đến bước cuối cùng, học sinh chỉ cần kết luận: "$x = -2$ hoặc $x = -3$".

Trong kiến trúc Transformer tiêu chuẩn, **mỗi token sinh ra trong quá trình nháp đều phải được lưu trữ vào bộ nhớ đệm KV (Key-Value Cache)** để các token tiếp theo có thể chiếu sự chú ý (attention) vào.

```
[Mô hình truyền thống - Full KV-Cache]
Prompt (Hệ thống + Tools) ────> [Nháp 1] ──> [Nháp 2] ──> ... ──> [Nháp 4000] ──> Kết quả
▲                                                                      │
└────────────────────────── Full Self-Attention ───────────────────────┘
  ==> Bộ nhớ KV Cache tăng tuyến tính O(N), VRAM tràn, tốc độ giải mã chậm dần đều!
```

Hậu quả:
1. **Lãng phí VRAM cực lớn:** Đến token thứ 4.000, GPU phải nạp và tính toán ma trận Attention trên toàn bộ 4.000 token nháp trước đó.
2. **Nghẽn băng thông bộ nhớ (Memory Bandwidth Bound):** Tốc độ sinh token (tokens/second) tụt dốc thảm hại khi chuỗi suy nghĩ kéo dài.

## 🖼 Trực Quan Hóa Bộ Nhớ: Full Attention vs Prefix Sliding

![Trực quan hóa cấu trúc bộ nhớ KV Cache Prefix Sliding](/images/deep-dives/prefix-sliding-kv-cache-architecture.webp)

> 💡 **Giải thích sơ đồ kỹ thuật trên:**
> * **Phía trên (Linear Memory Inflation):** Trong cơ chế Full Attention thông thường, mỗi token suy nghĩ (`<thought>`) sinh ra liên tục nạp vào KV-cache khiến bộ nhớ phình to tuyến tính $O(N)$. Đến token thứ 4.000+, dung lượng VRAM bị quá tải (Out-Of-Memory / OOM), tốc độ tính toán ma trận Attention tụt giảm mạnh.
> * **Phía dưới (Stanford Prefix Sliding):** Phân vùng bộ nhớ thông minh: **Pinned Prefix** (System Prompt, Tools) được khóa cố định bên trái; các token tư duy trung gian cũ bị loại bỏ (evicted) giải phóng VRAM; chỉ duy trì **Sliding Window 4.096 token** mới nhất bên phải. Kết quả: Tốc độ giải mã tăng vọt **$3\times$** mà không mất độ chính xác!


## 🚀 Giải Pháp Stanford: Prefix Sliding (arXiv:2608.26070)

Nhóm nghiên cứu tại Stanford (Muennighoff et al., công bố ngày 26/08/2026) đưa ra một nhận định đột phá:

> **"Mô hình không cần phải nhớ toàn bộ từng bước nháp xa xôi. Nó chỉ cần nhớ 2 thứ: (1) Yêu cầu ban đầu của đề bài (Prefix) và (2) Dòng suy nghĩ ngay trước mắt (Recent Window)."**

### Cơ chế hoạt động của Prefix Sliding

Prefix Sliding chia bộ nhớ KV-Cache thành 2 phân vùng cố định và di động:
1. **Pinned Prefix (Cố định):** Lưu giữ toàn bộ System Prompt, hướng dẫn nhiệm vụ, định dạng công cụ và schema đầu ra. Phần này **luôn được giữ lại 100%**.
2. **Sliding Reasoner Window (Cửa sổ trượt gần nhất):** Chỉ giữ lại khoảng $W$ token tư duy gần nhất (thường là $W = 4.096$ token). Toàn bộ các token nháp trung gian nằm giữa Pinned Prefix và Cửa sổ trượt sẽ bị **loại bỏ (evict) khỏi KV-Cache**.

```
[Kiến trúc Prefix Sliding]
┌─────────────────────────────────┐   ┌───────────────────────────────┐
│     PINNED PREFIX (Bảo lưu)     │   │ SLIDING WINDOW (W = 4096 tok) │
│ System Prompt + Tools + Context │ + │     Dòng tư duy mới nhất      │
└─────────────────────────────────┘   └───────────────────────────────┘
                                      ▲
                                      │ Cửa sổ trượt tịnh tiến theo thời gian
      (Các token nháp cũ ở giữa bị hủy bỏ khỏi KV-Cache giải phóng VRAM)
```

## 📊 Kết Quả Thực Nghiệm & Đo Lường

Các tác giả đã kiểm thử Prefix Sliding trên hàng loạt benchmark suy luận khó (MATH500, GPQA, Codeforces):

| Chỉ số đo lường | Full Attention CoT (Truyền thống) | Prefix Sliding ($W = 4096$) | Mức độ Cải thiện |
| :--- | :--- | :--- | :--- |
| **Tốc độ giải mã (Decoding Throughput)** | 28.4 tokens/giây | **87.2 tokens/giây** | **Nhanh hơn $\approx 3.07\times$** |
| **Dung lượng KV-Cache đỉnh điểm** | 12.8 GB / sequence | **3.2 GB / sequence** | **Tiết kiệm $75\%$ VRAM** |
| **Độ chính xác bài toán (MATH500)** | 84.6% | **84.4%** | $\pm 0.2\%$ (Không đổi đáng kể) |
| **Yêu cầu huấn luyện lại** | — | **Không cần (Zero-retraining)** | Áp dụng ngay lúc inference |

### Tại sao độ chính xác không bị tụt?
Các mô hình lý luận (Reasoning models) có tính chất tóm lược trạng thái: một bước suy nghĩ tốt ở bước $T$ đã cô đọng và phản ánh thông tin cần thiết từ các bước $T-1, T-2...$. Do đó, việc xóa bỏ các câu chữ nháp từ 2.000 token trước không làm mất ngữ cảnh lập luận cốt lõi, miễn là **System Prompt và mục tiêu ban đầu** vẫn được pin chặt ở đầu chuỗi.

## 🛠 Cách Triển Khai trong Inference Engine (vLLM / TensorRT-LLM)

Dưới đây là mã giả minh họa thuật toán quản lý block KV-cache theo nguyên lý Prefix Sliding:

```python
class PrefixSlidingKVCacheManager:
    def __init__(self, prefix_length: int, sliding_window_size: int = 4096):
        self.prefix_length = prefix_length
        self.window_size = sliding_window_size
        self.cache_blocks = []

    def allocate_or_evict(self, current_token_pos: int):
        total_tokens = current_token_pos
        
        # Nếu tổng token chưa vượt quá ngưỡng, giữ nguyên full attention
        if total_tokens <= (self.prefix_length + self.window_size):
            return
            
        # Vị trí cần cắt tỉa
        eviction_start = self.prefix_length
        eviction_end = total_tokens - self.window_size
        
        # Giải phóng các block nằm trong khoảng giữa prefix và window trượt
        self.evict_range(eviction_start, eviction_end)
```
